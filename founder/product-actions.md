# Что делать с продуктом после проверки

Это конкретный приоритетный backlog, а не отчёт о внесённых изменениях. Код, платежи, договорные условия и production-конфигурация этим исследованием не изменялись.

| Приоритет | Работа | Проверяемый результат | Опора |
|---|---|---|---|
| P0 | Допуск партнёра к продажам | Без подтверждённых условий/ответственного объект не предлагается как доступный коммерческий партнёр; наличие текущих признаков/флагов сначала проверить | Ответ владельца: согласившихся объектов 0 |
| P0 | Правила продажи места | Раздельно «место с подселением» и «отдельная комната»; нельзя обещать отдельную комнату при продаже только части кроватей | Риск модели мест; панель |
| P0 | Учёт прямых продаж | Квота или единый операционный календарь; конфликт не приводит к двум обещанным местам | Конкуренты продают напрямую; процессы партнёра неизвестны |
| P0 | Приёмка push | Закрыть внешние Apple/Firebase настройки, затем физический баннер/переход и отказ чужому менеджеру | docs/verification.md T003; backend/booking/push.py |
| P0 | Полная цепочка услуги | Оплата → бронь → остаток на месте → заселение → выезд → выдача документов, с обработкой отказов | Жалобы владельца; docs/verification.md |
| P1 | Карточка конкретного предложения | Цена за человека/сутки, состав, обязательные доплаты, фото реального размещения, условия детей | backend/booking/pricing.py v4; публичные прайсы |
| P1 | Понятный расчёт | Полная цена, онлайн-сейчас и на месте сходятся; не раскрывать чужие внутренние данные, не вводить в заблуждение о суммах | Пользовательская модель наценки; economics |
| P1 | Воронка без личных данных | События и знаменатели; реальные/тестовые операции разделены; никакого ИИН/телефона в аналитике | Сейчас 0 продаж; нет измеренного CAC |
| P1 | B2B onboarding | Один короткий сценарий: объект → места → цены → правила → обучение смены → контрольная бронь | Нужна воспроизводимая поставка партнёру |
| P2 | Повторные продажи и интеграции PMS | Делать после подтверждения спроса; оценить API текущей системы партнёра до её замены | TravelLine и прямые процессы уже существуют |

Не приоритет первого пилота: шардинг под миллионы запросов, государственные интеграции, универсальная медицинская карта, новые массовые рекламные каналы, новые визуальные переделки без наблюдений. Поддерживать безопасность/наблюдаемость/резервирование уже сейчас, но не выдавать архитектурную сложность за доказательство спроса.

## Контроль фактов
- Источник продуктовых правил: AGENTS.md, docs/api-contract.md и подтверждения владельца; никаких новых юридических выводов.
- pricing.py действительно умножает стоимость на chargeable_guests. Это source review, не новая проверка deployed калькулятора.
- push.py содержит проверки FCM/APNs и provider delivery. Это наличие кода, не факт настройки credentials или доставки.
- docs/verification.md описывает T003 и внешние блокеры. Текущие secrets/live устройства не проверялись в этом бизнес-разборе.
- В начале docs/product.md остаются устаревшие утверждения «API ещё не опубликованы» и «симулятор», противоречащие более позднему verification. Не использовать этот вводный текст как текущую истину; отдельная точечная синхронизация документации нужна после проверки live.
