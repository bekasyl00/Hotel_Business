# SRE: действующие механизмы и дальнейшее масштабирование

27 октября 2026. Связанные задачи единого реестра: R04, R15, R26–R30. Это **проект целевого устройства**, не доказательство работы на миллионной нагрузке. Тестов производительности в облаке ещё не было. Поставщик, бюджет, дежурная команда и численные SLO должны быть согласованы до запуска.

### Что хотим узнавать по сигналам

1. API доступен и может прочитать БД? `/health/live`, `/health/ready`, scrape `up`.
2. Очередь стоит или просто нет заказов? Постоянный heartbeat отдельно от oldest due/dead jobs.
3. Деньги требуют ручной сверки? `reconciliation_required` по provider/environment; без сумм и клиентов.
4. В БД заканчиваются соединения/есть ожидания блокировок? Снимки `pg_stat_activity`, не данные SQL/пользователей.

JSON request logs содержат только server-generated request ID, шаблон маршрута, method/status/duration. Сырые URL/query/body/IP/ИИН/секреты не включаются. Время в логе измеряет обработку Django, не загрузку страницы пользователем. Глобальные p95/5xx на дашборде не выдумываются из counters временного serverless процесса. Нужны надёжная выгрузка логов либо OTLP с collector/flush-бюджетом, затем RED/SLO alerts.

### Бесплатный старт и ограничения

Grafana Cloud Free: до 10 000 active metric series, 14 дней хранения; наш exporter имеет фиксированное небольшое число серий. Metrics Endpoint собирает HTTPS без отдельного Prometheus/Alloy сервера. Интервал 60 s — около 43 200 обращений/месяц, не нулевая стоимость API/DB ресурсов. [Grafana pricing](https://grafana.com/pricing/), [Metrics Endpoint](https://grafana.com/docs/grafana-cloud/observe-and-act/monitor-infrastructure/integrations/integration-reference/integration-metrics-endpoint/).

Live Supabase: Free, PostgreSQL 17, ap-northeast-2, около 22 MB DB на момент проверки. Это не запас на миллионы запросов. Free-проекту необходимы собственные регулярные экспорты; PITR/восстановление и read replicas требуют отдельного решения и проверки. [Backups](https://supabase.com/docs/guides/platform/backups), [pricing](https://supabase.com/pricing).

Live Vercel: Hobby. По условиям тариф предназначен для personal/non-commercial use, поэтому сервису с реальными оплатами нужен Pro либо другой подходящий хостинг. Подписка автоматически не меняется. [Hobby](https://vercel.com/docs/plans/hobby). Ни бесплатные планы, ни наличие графиков не гарантируют HA/SLA или заявленную масштабируемость.

Проверка 09.11.2026: cron за последний час запущен 60 раз, HTTP tick 200 во всех 60 ответах. Это свидетельство работы планировщика на тот момент, не тест оплаты/возврата и не пропускная способность.

Действующий [дашборд Grafana](https://bekasyl00.grafana.net/d/tynys-operations) доступен после входа в аккаунт. Сборщик использует `scrape_job="tynys-api"`; его внутренний `job` отличается от выбранного имени. Все шесть правил оцениваются раз в минуту. `service=tynys-api` направляет уведомления и восстановления на согласованный email аккаунта через contact point `Tynys administrator email`, с группировкой по папке/правилу/provider/environment. Это один email-канал, не круглосуточная дежурная служба. Инструкция разбора — [runbooks/operations.md](runbooks/operations.md).

При включении мониторинга найдено одно ожидающее задание `xpayment/sandbox/verify` старше суток. `TynysPaymentQueueDelayed` перешёл в Firing, Grafana отметила email как Delivered successfully. Production due/dead и просроченные holds в проверенном снимке — нулевые. Sandbox-задание не удалялось для получения зелёного статуса; подробности текущего состояния — в журнале проверки.

### Минимальные действия при сбое

- Нет scrape/heartbeat: проверить health ready, последний релиз, секреты сборщика и cron HTTP status. Не считать пустой график нулём ошибок.
- Растёт due/dead/reconciliation: сравнить heartbeat, leases и provider status. Не повторять неизвестный create/refund POST; восстановление только через независимый GET/ручную сверку.
- DB недоступна: API должен отказать, не писать во второй независимый источник. Откатить несовместимый релиз; failover лишь после проверки единственного writable primary и сверки платежей.
- Перед rollback: код совместим с добавленными таблицами/индексами, откатить Vercel deployment, миграции не удалять на горячей базе. Для `CREATE INDEX CONCURRENTLY` после прерывания проверить `pg_index.indisvalid`; не повторять вслепую имя невалидного индекса.

## Нагрузка, которую сначала нужно определить

«1 миллион пользователей в час» — не requests/second и не concurrent users. Иллюстрация для планирования: 1 000 000 сессий / 3600 ≈ 278 новых сессий/с; при 20 динамических запросах за сессию — около 5 556 средних API req/s. При сессии 10 минут получается около 166 667 одновременно активных сессий. Это расчёт допущений, не измерение и не характеристика Kaspi. Статические ресурсы, карта, видео и фоновые запросы считаются отдельно. Пиковый коэффициент и конверсия в брони требуют продуктовых данных.

Нужны четыре профиля: обычный каталог; старт сезонных продаж; одна популярная дата/санаторий; массовая повторная отправка после сетевого сбоя. Отдельно измеряем вход/SMS, чтение наличия, создание/подтверждение брони, платежные события, загрузки, отчёты и государственные внешние проверки. Не стрессовать Kaspi/SMS/госпорталы: их заменяют согласованные тестовые endpoints/заглушки с задержками и сбоями.

## Предлагаемые SLI/SLO (не обещанные значения)

- Успешность валидных чтений/записей ≥99,9% за 30 дней: budget 43,2 минуты. Ошибки клиента и корректный отказ «номер занят» считать отдельно, а не маскировать ими сбой. Отдельный SLI доступности внешних платежей/госисточников.
- На согласованной staging-нагрузке p95 ответа API каталога ≤300 ms, создания брони ≤800 ms, p99 ≤2 s. Измерять сервер и клиент отдельно, по регионам и cache hit/miss. Таймауты не выкидывать из выборки.
- Ноль подтверждённых пересекающихся броней одного места; ноль необъяснимых денежных расхождений; каждое принятое платёжное событие обработано либо явно находится на повторе/разборе.
- Свежесть доступности и время появления новой брони в кабинете: измеримый предел, первоначально предложено ≤5 s; окончательная запись всегда проверяет primary DB. Push/WebSocket — уведомление, не источник истины.
- Предварительные DR-цели: RPO ≤5 min и RTO ≤60 min, проверяемые восстановлением. Для финансов требуется повторная сверка с провайдером после restore; обычный backup не гарантирует отсутствие потерь.

[Google SRE: SLO](https://sre.google/sre-book/service-level-objectives/) — основа для выбора пользовательских показателей; числа выше являются нашими предложениями, не требованиями Google.

## Целевое устройство и порядок внедрения

1. CDN для веб-артефактов, публичных фото и версионированного каталога. Private-файлы и персональные API не кешировать публично. Каталог допускает ограниченную устарелость, write availability — нет.
2. Stateless Django API за балансировщиком, несколько реплик в пределах согласованного региона, pool соединений и лимиты concurrency. Считать `replicas × workers × connections`, оставлять резерв БД для администратора/миграций/очередей. Autoscaling ограничить мощностью БД и бюджета.
3. PostgreSQL primary — владелец inventory/booking/payment truth; транзакции, exclusion constraints, идемпотентность и версии. Реплики для чтения/аналитики только с обозначенной задержкой. Redis при необходимости — cache/лимиты, не замена PostgreSQL-lock для брони.
4. Transactional outbox + durable queue: уведомления, документы, медиа, сверка платежей. At-least-once доставка требует idempotent consumers, deduplication, retry backoff/jitter, DLQ и процедуры повторного исполнения. Платёжный webhook фиксируется до ответа; фактическое списание/возврат подтверждается провайдером.
5. Bulkheads для SMS/платежей/госисточников; таймауты и circuit breaker. Сбой портала льгот переводит проверку в pending, не превращает неподтверждённое право в одобрение. Сбой SMS не откатывает уже принятую бронь.
6. Для hot-sale: per-user/device/IP/resort quotas, bounded queue/ожидание, Retry-After и защита от бесконечных retries. Удержания inventory имеют согласованный TTL. На перегрузке сохраняем просмотр/свои брони и приостанавливаем тяжёлые отчёты/новые операции предсказуемо. [Google SRE: перегрузка](https://sre.google/sre-book/handling-overload/).
7. Разделение сервисов/партиционирование/шардинг вводить по замерам и границам данных. Не делать distributed booking transaction преждевременно. Regional/state-financed workflows выделяются логически раньше инфраструктурного разделения.

## Известные ограничения текущего кода

- Изменения каталога/брони сериализуются блокировкой строки санатория. Это обеспечивает согласованность, но может стать ограничением для одного популярного объекта. Нужен benchmark wait-time; переход на locks отдельных комнат требует единого порядка locks и тестов одновременно с изменением цен/архивированием. Просто удалить блокировку нельзя.
- `/workspace` и каталог возвращают большие наборы; пагинация, серверный поиск и отдельные списки обязательны до массовой загрузки. Новые pricePeriods prefetch исключают дополнительный запрос на каждый номер в списках, но не решают объём ответа целиком.
- Production payment queue уже хранится в PostgreSQL (PaymentJob), с lease/skip_locked, retry и dead-letter. Добавлены защищённые operational metrics, heartbeat и общие прикладные квоты. Общего transactional outbox для уведомлений, Redis, настроенных edge rate rules, traces и дежурства пока нет. Управление экземплярами выполняет Vercel; пропускная способность не измерена.
- Авторизованные видео в native-клиенте пока загружаются целиком; нужны потоковая выдача, разумные ограничения и обработка больших файлов вне web workers.
- Сейчас R12/R13 имеют max 60 ценовых периодов на номер и max 30 ночей на бронь. Программы с другими сроками требуют изменения правил, а не тихого обхода в UI.

## Что уже добавлено для эксплуатации

`GET /health/live` проверяет процесс без запроса БД; `GET /health/ready` выполняет `SELECT 1` в PostgreSQL. Возвращают только `ok`/`unavailable`, no-store, без имён серверов и секретов; readiness 503 при DatabaseError. SQL timeout 1 s, установление соединения ограничено существующим connect_timeout 10 s. Это не проверка миграций, S3, SMS или платежей. Readiness использовать для снятия реплики с трафика, liveness — для зависшего процесса; отказ БД не должен перезапускать все pods. Probe timeout/interval на балансировщике настроить под эти пределы, ограничить доступ/частоту на edge.

## Приёмка и эксплуатация

До пилота: отдельный staging с синтетическими данными; нагрузка только на разрешённую среду. Сначала baseline 10–50 req/s, затем ступени с согласованными лимитами, burst горячего объекта, 2–8 часов soak, outage DB/queue/provider, восстановление и повтор webhook. Повышать ступень после анализа, не объявлять миллионную ёмкость по маленькому тесту.

Сохранять: commit/config/hardware/data volume, профиль нагрузки и generator utilization, p50/p95/p99, throughput/errors/timeouts, DB CPU/IO/locks/connections/slow queries, queue lag, memory/GC, стоимость. Проверять инварианты после теста: пересечения, зависшие удержания, повторные оплаты, ledger discrepancy, orphan files. Размер данных должен соответствовать цели, включая историю.

Алерты: burn-rate SLO, рост 5xx/timeout, DB pool/lock waits, queue lag/DLQ, неподтверждённые платежи/возвраты, недоставленные уведомления, backup age/restore failure. Логи структурированные с request/trace ID и route/status/duration; без тела запросов, токенов, ИИН, SMS, медицинских сведений. Доступ к audit и логам ограничен и протоколируется.

Runbooks: DB outage, перегрузка санатория, дубль/зависший платёж, падение SMS/госпортала, недоступность private storage, утечка ключа, неудачная миграция, восстановление. Назначить on-call/эскалацию, критерий остановки продаж, статусную страницу, порядок уведомления пользователей и postmortem без поиска виноватого. Deploy: small batch/canary, compatible API, expand-contract миграции, feature flags и rehearsed rollback. Старые версии установленных приложений поддерживаются до согласованной даты.
