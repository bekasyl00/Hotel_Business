# Ограничения запросов

`booking/rate_limits.py` использует общие PostgreSQL-счётчики `LoginAttempt`: один бюджет действует для всех web/API workers, обеих версий `/api` и `/api/v1`, а вход — также для native-клиентов. Это прикладная защита, не поглощение DDoS: запрос уже дошёл до Django и базы. Лимиты на edge остаются отдельной задачей.

Каждое фиксированное окно начинается с первого запроса. `SELECT FOR UPDATE` сериализует изменения; несколько ключей блокируются в одном порядке. Отказ возвращается после завершения транзакции счётчиков: ошибки в последующей операции не возвращают её квоту. Ответ API — HTTP 429, `code: rate_limited`, целое количество секунд в `Retry-After`, `Cache-Control: no-store`. Пограничный момент ровно в конце окна разрешает новый бюджет. Повторять изменяющий запрос автоматически нельзя; у брони сохраняется прежний requestId.

Стоимость одного IP-счётчика измеряется отдельно от предметного запроса: 7 SQL-команд для отсутствующей строки и 4 для существующей (включая управление транзакцией/вложенными savepoints). Календарь сохраняет прежние 4 предметных чтения: санаторий, подходящие номера, цены периода, занятые интервалы. Тесты проверяют обе части бюджета без отключения лимитера. Это дополнительная нагрузка PostgreSQL; при росте RPS сначала измеряются её задержки и блокировки, затем рассматривается внешний общий лимитер/edge, а не локальная память отдельного worker.

| Операция | Ключи и предел |
| --- | --- |
| Создание брони | 30 на подтверждённую сервером личность гостя/сотрудника и 120 на IP за 15 минут; перед транзакцией создания |
| Наличие и календарь | 300 на IP за минуту, до расчёта |
| Вход сотрудников | 30 на email и 30 на IP за 15 минут; web и native используют общий бюджет |
| Вход гостей | 10 на телефон и 30 на IP за 15 минут |
| Регистрация без SMS | 5 на телефон и 20 на IP за час |
| Запрос кода | 5 на телефон и 30 на IP за час; повторная отправка дополнительно ограничена 60 секундами |
| Изменение/обновление платежа | Существующий предел 60 на IP за 5 минут |
| Выгрузка бухгалтерии | 60 на IP за 5 минут; проверка до финансовых агрегаций/формирования файла |
| Некорректная подпись XPayment | 120 на IP за минуту; корректно подписанные события этот бюджет не расходуют |

Отдельные квоты редакторов, сканера и реквизитов остаются на своих API. Подписанные уведомления XPayment ограничены размером 16 KiB и проверкой подписи; постоянный `WebhookDelivery` устраняет повторную постановку задачи одного delivery ID. Подпись не подтверждает оплату: сервер по-прежнему независимо проверяет провайдера. Halyk sandbox сохраняет существующий отдельный IP-бюджет уведомлений.

Обычно IP берётся из `REMOTE_ADDR`. В Vercel runtime (`VERCEL=1`, серверная настройка `VERCEL_RUNTIME`) принимается только единственный корректный IPv4/IPv6 из `X-Vercel-Forwarded-For`: Vercel перезаписывает этот заголовок адресом клиента. Цепочки адресов, Unicode, пустые и ошибочные значения отклоняются с возвратом к `REMOTE_ADDR`. Обычные `X-Forwarded-For` и `X-Real-IP` не принимаются. Основание: [документация заголовков Vercel](https://vercel.com/docs/headers/request-headers#x-vercel-forwarded-for). На другом хостинге флаг включать нельзя: его доверенный прокси нужно настроить отдельно. Все IP-квоты, включая вход staff/admin, используют один helper. На больших NAT пользователи разделяют IP-бюджет; значения надо пересматривать по метрикам 429, а не увеличивать вслепую.

Счётчики содержат digest ключа, число и начало окна, без исходного телефона/IP. Старые ключи staff/admin сохранены для непрерывности бюджетов при обновлении. Нет таймера удаления в обработчике запроса. Ежедневная эксплуатационная задача:

```sh
backend/.venv/bin/python backend/manage.py cleanup_rate_limits --days 7 --limit 1000
backend/.venv/bin/python backend/manage.py cleanup_rate_limits --days 7 --limit 1000 --delete
```

Первая команда — просмотр количества кандидатов без удаления; вторая удаляет до 1000 строк. Допустимо 7–365 дней и 1–5000 строк за запуск. Блокированные активным запросом строки пропускаются (`skip_locked`). Phone-scope строки, используемые для сериализации выдачи/проверки SMS и регистрации, обновляют время при использовании и безопасно создаются заново после очистки. Индекс `booking_rate_since_idx` добавляется concurrent-миграцией 0016 без переписывания таблицы. Команда подготовлена; наличие ежедневного расписания проверяется отдельно, само её существование не означает запущенный cron.

Проверки: конкурентные PostgreSQL workers не превышают квоту; окно и Retry-After; неизменность квот при подставленном forwarded IP; счётчик не откатывается вместе с отказавшей бронью/чтением реквизитов; экспорт блокируется до агрегации; валидный XPayment webhook проходит при исчерпанной квоте неправильных подписей; очистка ограничена и пропускает удерживаемые блокировки.
