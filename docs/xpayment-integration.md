## Контракт провайдера

Основные источники — [OpenAPI v2](https://xpayment.kz/openapi/xpayment-api-v2.json), [v1](https://xpayment.kz/openapi/xpayment-api-v1.json) и [кабинет песочницы](https://xpayment.kz/app/sandbox). Новый рекомендуемый API v2 пока помечен поставщиком beta. Базовый адрес `https://api.xpayment.kz/v2`, ключ `xapi_…`, обязательный `device_name` при создании. Адаптер сохраняет совместимость с v1 для ранее настроенных устройств. v2 проверяет имя кассы в каждом прочитанном платеже и фильтрует восстановление по кассе и заказу. Старые примеры блога местами расходятся со схемой; адаптер не смешивает эти формы.

| Операция | Документированный контракт |
| --- | --- |
| Создать оплату | `POST /payments/link`, сумма в KZT и `merchant_order_id`; ответ содержит `payment_id`, `qr_token`, `expire_date` |
| Восстановить после сбоя | `GET /payments?merchant_order_id=…`, затем `GET /payments/:payment_id`; при пагинации или нескольких записях остановить автоматическую обработку для сверки |
| Проверить оплату | `GET /payments/:payment_id`: сверить `user_id`, заказ, сумму, валюту и статус |
| Отменить ожидание | `POST /payments/:payment_id/cancel`, затем независимая проверка состояния |
| Возврат | `POST /payments/:payment_id/refund`, затем `GET /payments/:payment_id/refunds`; HTTP 202 не означает завершение |

Для link/refund не опубликована гарантия `X-Idempotency-Key`; неизвестный исход POST нельзя повторять вслепую. GET/list не возвращает исходный QR и срок, поэтому найденная после сбоя запись не позволяет выдумать новую ссылку. `expire_date` ответа сокращает доступность ссылки и hold брони до более раннего из двух сроков; срок никогда не продлевается. Если восстановление не вернуло срок/QR, новая ссылка не выдумывается, действует сохранённый hold и независимая проверка. API банковского/фискального чека не описан: `receiptUrl` остаётся пустым, PDF симулятора не выдаётся за документ Kaspi.

## Настройки Django

Шаблон: `backend/.env.xpayment.example`. Офлайн-проверка без сетевых запросов: `backend/.venv/bin/python backend/manage.py check_xpayment` (с указанием нужного `PAYMENTS_ENV_FILE`).

Все значения — только в серверном secret storage или игнорируемом локальном env. Ключи, OTP и webhook secret не отправляются в чат, Git, браузерную сборку, аналитику или журнал.

| Переменная | Назначение |
| --- | --- |
| `PAYMENT_PROVIDER=xpayment` | Провайдер новых банковских попыток; старые попытки сохраняют свой провайдер |
| `XPAYMENT_ENABLED=false` | Закрытый по умолчанию операционный переключатель |
| `XPAYMENT_PROTOCOL_VERIFIED=false` | Отдельный закрытый флаг реальной денежной приёмки |
| `XPAYMENT_SANDBOX_PROTOCOL_VERIFIED=false` | Независимый флаг приёмки песочницы; не открывает production |
| `XPAYMENT_API_VERSION` | `v2` для нового подключения; `v1` по умолчанию для совместимости |
| `XPAYMENT_PRODUCTION_RESORT_IDS` | Разрешённые санатории реальной кассы через запятую; пустой список запрещает новые production оплаты |
| `XPAYMENT_ENV` | `sandbox` либо `production`, совпадает с префиксом ключа |
| `XPAYMENT_DEVICE_NAME` | `test` для песочницы v2; реальное имя кассы для production v2 |
| `XPAYMENT_API_KEY` | `xapi_test_…` для sandbox v2, `xapi_…` для production v2; legacy v1 использует `xdev_…` |
| `XPAYMENT_ACCOUNT_ID` | UUID аккаунта провайдера, совпадающий с `user_id` проверяемого платежа |
| `XPAYMENT_WEBHOOK_SECRET` | Независимый случайный секрет длиной не менее 32 символов |

При использовании `PAYMENTS_ENV_FILE` уже заданные переменные процесса/основного env имеют приоритет. Установить `PAYMENT_PROVIDER=xpayment` также в основной конфигурации развёртывания и проверить `check_xpayment`; не рассчитывать на переопределение старого значения вторым файлом.

`production` означает реальные денежные операции, а не завершение production readiness. `sandbox` использует те же HTTPS endpoints, но только тестовые ключи; смешение префикса и окружения отвергается до сетевого запроса. Merchant scope включает окружение и, для v2, имя кассы. Смена окружения/кассы не перенаправляет старые jobs: они ждут восстановления своей конфигурации. Не включать флаги только потому, что заполнены настройки. Старые Halyk sandbox и Kaspi-themed demo не переименовываются в XPayment и не смешиваются с реальными поступлениями.

## Webhook и подтверждение брони

Адрес подписки: `https://<API-домен>/api/v1/payments/providers/xpayment/callback`. Для текущего домена API это `https://tynys-api.vercel.app/api/v1/payments/providers/xpayment/callback`; подписка создана, доставка событий оплаты/возврата в опубликованный API подтверждена; секрет хранится только у провайдера и в закрытой серверной конфигурации.

Поставщик описывает [события и доставку](https://xpayment.kz/blog/webhooks) и [проверку подписи](https://xpayment.kz/blog/webhook-security): `X-xPayment-Signature` — HMAC-SHA256 от исходных байтов тела, hex без префикса. Повтор содержит тот же `delivery_id`, но новое `attempt_number`; подписанный тестовый `payment.completed` тоже не является оплатой. Django проверяет подпись, допустимую оболочку и окружение (sandbox обязательно содержит `environment=sandbox`; legacy production допускает отсутствие поля), сохраняет дедупликацию в PostgreSQL и ставит независимую GET-сверку. Только проверенное сервером завершение с совпадением владельца аккаунта, заказа, суммы и валюты может подтвердить ещё действующую бронь. Redirect, QR и callback сами не подтверждают оплату. Поздняя оплата и расхождения остаются в сверке, без повторной продажи номера.

### Диагностика недоставленных уведомлений

HTTP401 нашего callback означает несовпадение HMAC-подписи: сверить production/sandbox конфигурацию и секрет подписки с **опубликованным** runtime, не только локальным env. Не отключать подпись и не возвращать фиктивный 2xx. 08.11 production-подписка начала работу до публикации новой конфигурации; после деплоя реальный `payment.cancelled` доставлен HTTP200 с первой попытки. Старые 401 остаются историей. `WebhookDelivery` подтверждает приём, но платёж подтверждается только отдельным GET провайдера.

Проверять pending/running/dead jobs и независимое состояние счёта. После 10 неудачных попыток job становится `dead`; callback намеренно не сбрасывает backoff/dead во избежание бесконечных повторов. Автоматический алерт и контролируемая процедура восстановления dead jobs ещё нужны (R27). Не повторять неоднозначный create/refund POST: сначала GET/list и сверка сохранённого заказа.

Миграция `commerce.0004` расширяет идентификатор заказа и вводит допустимые пары провайдера/среды, а также таблицу дедупликации. После появления XPayment-записей откат к sandbox-only ограничению или 15 символам небезопасен; исправления выполнять следующей миграцией. Закрытие новых оплат сохраняет обработку уже начатых операций и возвратов; отсутствие/смена merchant credentials оставляет задания для восстановления правильной конфигурации.


## Песочница API v2 — 8 ноября 2026

В кабинете «Песочница» используется касса `test`. Владелец создал отдельный ключ `xapi_test_…` и сохранил в игнорируемом `backend/.env.xpayment.sandbox` (0600), а не в переписке. Production-настройки хранятся отдельно; опубликованный в чате ключ перед реальным пилотом нужно заменить. Значения ключей/секретов в документацию не копируются.

Тестовый исход задаётся документированной в кабинете операцией `POST /v2/sandbox/payments/:id/simulate`, `outcome=paid|declined|expired|failed`. Это операция песочницы XPayment, не банковский CHARGE. Приложение по-прежнему ждёт независимый GET, который проверяет merchant/order/device/amount/currency; нельзя открывать simulate endpoint клиентам нашего API. Для тестовых подписок у провайдера отдельный раздел, production-подписки эти события не получают. QR-ссылка показывает сумму/статус без кнопки симуляции; исход задаётся в авторизованном кабинете «Песочница» или серверным API. Публичным клиентам ключ/endpoint симуляции не передаётся. Ссылка действует 5 минут и сокращает hold. Возврат ровно 13.13 KZT документирован поставщиком как тестовый отказ.

Приёмка: создание ссылки → проверка статуса → подписанный callback → GET → атомарное подтверждение одной брони; повтор callback; пропущенный callback через scheduler; отмена/истечение; полный и частичный возврат; отсутствие записей sandbox в production-аналитике. Затем отдельная реальная приёмка с согласованной суммой/возвратом и финансовыми реквизитами. После sandbox-приёмки `XPAYMENT_ENABLED=true` и `XPAYMENT_SANDBOX_PROTOCOL_VERIFIED=true` разрешают только тестовую среду. `XPAYMENT_PROTOCOL_VERIFIED=false` продолжает запрещать реальные оплаты. API v2/настройка кассы сами по себе не закрывают R16.

Наблюдение настоящего sandbox API: и create, и GET возвращают `QR_TOKEN_CREATED` (ожидание), ссылки вида `https://xpayment.kz/sandbox/qr/<digits>`; sandbox ответы содержат `environment=sandbox`. Адаптер учитывает это, не разрешая тестовой попытке открыть реальный Kaspi checkout. Предыдущий v1 вариант `QrTokenCreated` также поддерживается для create.

## Наблюдения при сквозной проверке

- Реальный sandbox провайдера проверен для paid, declined, failed, expired и отмены. Две вымышленные брони общего Django/Supabase автоматически подтвердились после GET; кабинет сотрудника видит обе. Отмена через опубликованный API дала окончательные возвраты 24 000 и 16 800 KZT (100%/70%), по одному применённому charge/refund событию, все в sandbox.
- Refund-list фактически использует `{data, total}`. Адаптер требует полного списка; частичный/неизвестный ответ не доказывает отсутствие возврата. После возврата родительский платёж имеет `REFUNDED`/`PARTIALLY_REFUNDED`, сохраняет исходную сумму и никогда не превращается в новый CHARGE. Точный возврат подтверждается отдельной записью возврата.
- Немедленная отмена в `QR_TOKEN_CREATED` может временно не пройти; после независимой проверки и перехода в PENDING повтор обрабатывается job. Неизвестный результат refund/link не разрешает слепой повтор POST.
- Проверки sandbox не доказывают работоспособность реального Kaspi, банковского чека, split, SLA или нагрузочную ёмкость. Последняя опубликованная версия и проверки указаны в verification.md.

## Боевой API и открытие Kaspi

Фактическое поле `environment=live` принимается только как внешний синоним production в create/GET/refund/callback. Неизвестные значения запрещены; sandbox никогда не принимается за production. Подписанный callback только запускает независимую проверку.

API выдаёт `https://qr.kaspi.kz/<digits>` для открытия в приложении Kaspi или сканирования QR. Обычный desktop HTTP GET может вернуть 404: это не страница песочницы. Владелец подтвердил работу ссылки, оплатив с телефона; сервер отдельно проверил CHARGE. Не заменять URL придуманным kaspi://. QR строится локально из проверенной ссылки, без передачи данных стороннему QR-сервису.

Создание ссылки и сверка пока ждут минутный scheduler. UI показывает подготовку ссылки, затем действие оплаты. Браузерное возвращение не является подтверждением. Старые брони с sandbox attempt сохраняют его; для реальной оплаты нужна новая бронь. Настоящий перевод возврата этого этапа не выполнялся по решению владельца; код использует тот же frozen merchant/environment и независимую проверку суммы/статуса.
