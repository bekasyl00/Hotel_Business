# Операционные действия по сигналам мониторинга

Владелец всех шести сигналов — **администратор платформы Бекасыл** (`owner=platform-admin`). Выделенная дежурная команда и круглосуточная поддержка пока не утверждены. `severity=page` означает необходимость оперативной проверки выбранного контакта; `severity=ticket` — запись задачи и разбор задержки. Эти метки сами не отправляют уведомления: необходимы contact point, notification policy и проверка доставки в Grafana.

Пороги ниже — начальные настройки пилота, не подтверждённые SLO. Плановый tick выполняется раз в минуту; очередь должна сохранять запас внутри 15-минутного удержания брони (оно может закончиться раньше в момент заезда). Пяти минут ожидания достаточно для расследования: ещё две минуты `for` отсекают единичный медленный запрос, оставляя около восьми минут стандартного hold. Это бюджет для реакции, а не гарантия успеть обработать платёж. Порог следует уточнять по наблюдениям и лимитам провайдера; не увеличивать его только ради зелёного dashboard.

Начало любого разбора: записать время, имя сигнала, environment/provider/kind и обезличенный request ID. Проверить свежесть наблюдения. Не помещать в задачи/скриншоты токены, ИИН, телефоны, полные запросы провайдера или банковские реквизиты. После исправления убедиться в новом успешном наблюдении и восстановлении состояния; не закрывать инцидент только потому, что истёк временной ряд.

<a id="metrics-scrape"></a>
## Сбор метрик недоступен

**Сигнал:** `TynysMetricsScrapeUnavailable`, `up=0` или отсутствует 3 минуты. Три последовательных интервала уменьшают шум от одиночного сетевого сбоя, но не скрывают потерю наблюдаемости.

1. В Grafana Metrics Endpoint проверить статус job `tynys-api`, последний сбор и HTTP-код. Проверить доступность `/health/live` и `/health/ready` API без токена метрик.
2. При 401 сверить защищённые настройки Bearer у сборщика и `METRICS_BEARER_TOKEN` в текущем Vercel deployment. При 404 проверить настройку метрик/версию релиза. При 503 перейти к проверке БД. Не печатать токен и не отключать авторизацию ради проверки.
3. При сетевой ошибке проверить Vercel/Supabase status и журнал последнего deployment. Восстановить ошибочную настройку либо вернуться к совместимому предыдущему API-релизу; миграции финансовой истории назад не удалять.
4. Закрытие: минимум два новых успешных scrape, `up=1` и свежий `tynys_metrics_snapshot_timestamp_seconds`. Отсутствие данных не считать нулевой нагрузкой.

<a id="metrics-snapshot"></a>
## Нет свежего снимка приложения

**Сигнал:** `TynysMetricsSnapshotStale`, при успешном scrape timestamp отсутствует либо старше 180 секунд ещё 3 минуты. Проверка отделяет доступность exporter от достоверности прикладных данных; при `up=0` действует предыдущий сигнал.

1. Проверить datasource/job в Explore и версию опубликованного endpoint. Подтвердить, что собирается `/internal/metrics`, а не HTML/другой Prometheus target.
2. Проверить clock/timestamp, `Cache-Control: no-store` и отсутствие кеширующего proxy перед endpoint. Затем проверить `/health/ready`, SQL timeout и доступность PostgreSQL.
3. Исправить конфигурацию/совместимую версию exporter; не подставлять `0` вместо неизвестных значений.
4. Закрытие: timestamp обновляется на каждом из двух следующих сборов; возраст соответствует интервалу 60 секунд.

<a id="scheduler"></a>
## Плановый обработчик не завершает работу

**Сигнал:** `TynysSchedulerSuccessStale`, последний успех `payment_scheduler` старше 300 секунд ещё 2 минуты. Нулевой timestamp означает, что успеха ещё не было. Успех CLI `payment_worker` этот сигнал не отменяет.

1. Проверить включённость расписания pg_cron, последние результаты pg_net и HTTP-статус защищённого tick. Не выводить тела команд cron/заголовки, в которых может быть секрет.
2. При 401 проверить сохранённый scheduler secret в Vault и Vercel. При timeout/5xx сопоставить обезличенные request IDs, время выполнения, leases и состояние PostgreSQL.
3. Восстановить расписание/связность/совместимый deployment. Ручной запуск использовать только как контролируемое восстановление обработки, а не замену расписания. Не запускать параллельные обработчики без проверки БД и лимитов внешнего провайдера.
4. Закрытие: два последующих плановых tick завершились успешно, timestamp `payment_scheduler` свежий, очередь due уменьшается.

<a id="payment-queue"></a>
## Платёжная очередь отстаёт

**Сигнал:** `TynysPaymentQueueDelayed`, самая старая готовая задача ожидает более 300 секунд ещё 2 минуты. Будущий retry backoff не считается задержкой; начальный бюджет выбран относительно 15-минутного hold.

1. Проверить environment/provider/kind сигнала, scheduler heartbeat, due depth и oldest age. Sandbox и production разбирать отдельно.
2. Проверить leases, provider timeout/ограничения и нагрузку БД. При растущей очереди реальных оплат эскалировать администратору немедленно, хотя исходная метка — `ticket`.
3. Исправить причину и дать штатной очереди восстановиться. Увеличивать batch/concurrency только после проверки длительности tick, резервов соединений БД и лимитов провайдера. Не добавлять повторный create/refund POST при неизвестном результате предыдущего.
4. Закрытие: oldest due ниже порога и depth устойчиво снижается; просроченные платежи отдельно прошли серверную сверку, а не получили подтверждение по времени/redirect.

<a id="dead-job"></a>
## Задание остановлено после ошибки

**Сигнал:** `TynysPaymentJobDead`, хотя бы одна dead-задача сохраняется 1 минуту. Повторный сбор подтверждает постоянное состояние; ожидать пять минут здесь нет смысла, потому что штатный retry прекращён.

1. Проверить provider/environment/kind и код ошибки в закрытом операторском доступе. Разобрать отдельно тестовые и реальные попытки.
2. Проверить frozen provider/environment/merchant binding и независимо прочитать состояние операции у провайдера. Подписанный webhook сам по себе не доказывает успешную оплату/возврат.
3. Устранить причину; повторное исполнение допустимо только после определения внешнего результата и сохранения идемпотентности. Не удалять dead-запись, не сбрасывать started-маркеры, не ставить paid/refunded вручную для очистки графика.
4. Закрытие: оператор зафиксировал результат сверки; безопасный сервисный workflow обработал или перевёл запись в подтверждённое конечное состояние. История платежа сохранена.

<a id="reconciliation"></a>
## Реальный платёж или возврат требует сверки

**Сигнал:** `TynysProductionReconciliationRequired`, есть production-запись `reconciliation_required` в течение 2 минут. Порог — повторное подтверждение наблюдения, а не разрешение задерживать разбор денег.

1. Администратор платформы сверяет попытку и возврат в закрытом кабинете с аутентифицированными данными провайдера: binding, внешний идентификатор, collected online amount, фактический статус. Сумма проживания и onsite-отметка сотрудника не являются банковским поступлением платформы.
2. Проверить late payment после истечения hold, неоднозначный create/refund, повторные callbacks и несоответствия суммы. Не подтверждать повторно проданный номер и не инициировать второй возврат до выяснения первого результата.
3. Выполнить только подтверждённое сервисное действие/сверку; при недостаточных данных оставить состояние на разборе и обратиться к провайдеру через закрытый согласованный канал.
4. Закрытие: есть независимое доказательство провайдера и соответствующее ему серверное конечное состояние; финансовая история и документы не переписаны. Отмена сигнала сама по себе не подтверждает поступление клиенту.
