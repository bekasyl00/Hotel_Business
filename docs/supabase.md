# Supabase: PostgreSQL и закрытое хранилище

Проект: `https://uchqzxxqioixhzbnwcak.supabase.co`. На 23 октября 2026 года через официальный Supabase connector применена начальная миграция `bootstrap_private_django_schema` и создан закрытый bucket `tynys-private`. Это подготовленная облачная инфраструктура. Подключение запущенного Django к PostgreSQL и S3 пока **не проверено**: пароль подключения и S3 credentials ещё не настроены. Сам Django требуется разместить отдельно от статических сайтов Vercel.

Проверенное состояние облачной базы PostgreSQL 17.11:

- Схема `tynys`: 25 таблиц, у всех включён RLS; в `django_migrations` 26 записей.
- Пользователей сотрудников, гостевых аккаунтов и бронирований нет; локальные тестовые/личные данные не переносились.
- `anon` и `authenticated` не имеют `USAGE` на `tynys`; клиентские RLS-политики отсутствуют. В bootstrap также отозваны права `PUBLIC` на схему и её объекты.
- Ограничение `no_overlapping_active_bookings` присутствует; `btree_gist` установлен в `extensions`.
- Security advisors показал 25 информационных сообщений о RLS без политик. Здесь это намеренный запрет клиентского доступа, а не доказательство готовности серверной роли.
- Bucket `tynys-private` имеет `public=false`, лимит 40 MiB и MIME `image/jpeg`, `video/mp4`, `video/webm`. Реальная загрузка/выдача файлов через Django ещё не проверена.

## Граница ответственности

Сайт, кабинет сотрудников и будущие iOS/Android-клиенты обращаются к Django `/api/v1`. Django проверяет аккаунт, принадлежность данных санаторию, наличие номеров, стоимость и переходы брони. Supabase используется как PostgreSQL и S3-совместимое хранилище; Supabase Auth/Data API в текущем приложении не используются. Секреты БД и S3 не должны попадать в `VITE_*`, браузер, мобильное приложение или Git.

## Подключение базы

1. В панели проекта открыть **Connect**. Для постоянного Django-сервера выбрать direct connection при доступном IPv6 или session pooler при IPv4. Строку брать из панели, включая точное имя пользователя и регион. Для миграций предпочтителен direct connection. [Официальные способы подключения](https://supabase.com/docs/guides/database/connecting-to-postgres).
2. Использовать уже созданную схему `tynys`; не добавлять её в exposed schemas Data API. Не повторять bootstrap поверх существующей схемы и не переносить локальную базу с тестовыми аккаунтами.
3. После настройки соединения выполнить обычный `manage.py migrate` отдельной миграционной ролью. Схема и журнал миграций уже созданы, но Django должен выполнить `post_migrate`, чтобы заполнить служебные `contenttypes` и permissions. Последующие изменения схемы вносить Django-миграциями, а не повторным SQL-снимком.
4. До production создать отдельную серверную runtime-роль без владения таблицами, `SUPERUSER`, `BYPASSRLS`, `CREATEDB`, `CREATEROLE` и прав изменения схемы. Ей нужны согласованные права на таблицы/последовательности **и соответствующие RLS-политики только для этой серверной роли**. Одних `GRANT` недостаточно: RLS без политик отклоняет доступ обычной роли. Не обходить это запуском production Django под владельцем таблиц/`postgres` или выдачей `BYPASSRLS`. Внешние `anon` и `authenticated` не получают этих политик/прав; Django по-прежнему проверяет владельца гостевых данных и область санатория. [Граница Data API](https://supabase.com/docs/guides/api/securing-your-api).
5. В секретных настройках сервера задать `DATABASE_URL`, `DB_SCHEMA=tynys`, `DB_SSLMODE=verify-full`, `DB_SSLROOTCERT` — путь к CA сертификату из панели проекта. Не отключать проверку TLS. `DB_CONN_MAX_AGE=60` и health-check включены. Transaction pooler для обычного Django не является режимом по умолчанию; если выбран осознанно, `DB_TRANSACTION_POOLER=True` отключает persistent connections, server-side cursors и prepared statements.

Для настроек облачного соединения подготовлен игнорируемый Git файл `backend/.env.supabase`. По умолчанию Django читает `backend/.env`; переменная `DJANGO_ENV_FILE` выбирает другой файл. Уже заданные переменные окружения имеют приоритет над содержимым файла. Секреты должны задаваться в защищённых настройках сервера или локально в игнорируемом файле, а не в чате/репозитории.

После заполнения необходимых секретов, из корня репозитория:

```sh
DJANGO_ENV_FILE=backend/.env.supabase backend/.venv/bin/python backend/manage.py check
DJANGO_ENV_FILE=backend/.env.supabase backend/.venv/bin/python backend/manage.py migrate
```

Эти команды пока не подтверждены для облачного runtime. Перед production надо проверить доступ runtime-роли без привилегий владельца, вход сотрудника/гостя и конкурентное бронирование через Django. При каждой новой миграции проверить RLS новых таблиц, отсутствие прав PUBLIC/anon/authenticated, серверные политики и default privileges для фактической миграционной роли. `ALTER DEFAULT PRIVILEGES` не включает RLS автоматически. Не менять `search_path` заполненной базы без плана переноса.

## Воспроизводимый bootstrap

`scripts/export-django-schema.py` создаёт две временные базы только на loopback PostgreSQL 17. В первой применяет реальные Django-миграции в `tynys`, экспортирует `pg_dump --schema-only --no-owner --no-privileges`; во второй восстанавливает полученный SQL и проверяет результат. Он не читает пользовательские строки текущей базы, не подключается к Supabase и удаляет только созданные им временные базы.

В SQL входят структура и `app/name` журнала миграций, без переноса исходных ID, пользователей, секретов, контента и бронирований. Транзакция содержит защиту пустой схемы, создание `btree_gist` в `extensions`, отзыв клиентских прав и включение RLS. Повторное применение к заполненной схеме отклоняется. Перед cloud-применением локально подтверждены 25 таблиц, 26 записей миграций, пустые остальные таблицы, отсутствие PUBLIC-доступа и клиентских политик; `migrate --check` прошёл, обычный `migrate` сообщил `No migrations to apply.`.

Пример для подготовки **нового** проверяемого артефакта из локального окружения:

```sh
backend/.venv/bin/python scripts/export-django-schema.py --output output/bootstrap-review.sql
```

Артефакт текущего bootstrap: `output/supabase-bootstrap-20261023.sql`, 56 771 байт, SHA256 `d09e525d407e569ad75ac5bec1fa03297a14a02363558122818024580bc1ba6a`. Расширенный локальный отчёт: `output/supabase-bootstrap-verified-20261023.json`. Каталог `output` игнорируется Git. Эти локальные проверки отдельно от последующей проверки облачной схемы, указанной выше; они не проверяют Django runtime в облаке.

## Фото и видео

Закрытый bucket `tynys-private` уже создан с указанными выше ограничениями. В S3 settings остаётся получить endpoint, region и создать серверные S3 credentials. S3-ключи обходят Storage RLS и дают доступ к bucket-ам проекта, поэтому хранятся исключительно на Django-сервере. [S3 authentication Supabase](https://supabase.com/docs/guides/storage/s3/authentication).

Настройки перечислены в `backend/.env.example`:

```dotenv
MEDIA_STORAGE=supabase
SUPABASE_S3_ENDPOINT=https://uchqzxxqioixhzbnwcak.storage.supabase.co/storage/v1/s3
SUPABASE_S3_REGION=copy-from-project-settings
SUPABASE_STORAGE_BUCKET=tynys-private
# SUPABASE_S3_ACCESS_KEY_ID и SUPABASE_S3_SECRET_ACCESS_KEY — только secret storage сервера.
```

Используется стандартный Django storage backend `django-storages` с boto3. Загрузки идут через Django multipart API. JPEG/PNG/WebP декодируются и перекодируются в JPEG без EXIF, поэтому bucket принимает для изображений `image/jpeg`; staff может загружать MP4/WebM. `MediaAsset` хранит владельца/назначение, MIME, размер, ключ объекта и дату. Клиент получает постоянный `/api/media/files/<id>`, а не публичную ссылку на bucket. Django проверяет доступ при чтении и при настроенном S3 выдаёт подписанную ссылку на 60 секунд. Эти ссылки нельзя записывать в логи/аналитику. Отозванная уже выданная ссылка может действовать до окончания этих 60 секунд. Наличие bucket пока не подтверждает этот путь загрузки/чтения через приложение.

Аватар доступен самому гостю и сотрудникам с соответствующей бронью; фото не публикуется вместе с отзывом. Фото каталога доступны публично только после привязки к опубликованному санаторию/активному номеру. Фото отзыва доступны публично после одобрения. Черновики доступны владельцу или сотруднику в его области доступа.

Локально файлы лежат в игнорируемом `backend/private-media`, выдаются тем же API и поддерживают HTTP Range для воспроизведения видео. Старый `backend/mediafiles` обслуживает только прежние демонстрационные файлы. При переводе уже заполненного локального хранилища в S3 объекты надо скопировать с сохранением storage_key и проверить контрольные суммы; одно изменение `MEDIA_STORAGE` ничего не переносит.

## Проверка перед переключением живого сайта

- `check`, миграции, `collectstatic`; резервная копия и тест восстановления.
- Оба сайта собрать с `VITE_DATA_MODE=api`; `/api` проксировать к одному Django. Для веба оставить same-origin proxy, cookie/CSRF; CORS wildcard не нужен. Django Admin разместить на отдельном адресе сервера/операционного домена, `/django-admin/`.
- В реальном bucket проверить загрузку, чтение, Range видео, отказ чужому гостю/управляющему и удаление тестового объекта. Локальные тесты не доказывают доступность облака.
- Запланировать `cleanup_media` (сначала dry run, затем `--delete`) и `cleanup_mobile_sessions`. `cleanup_media` удаляет только файлы с учтёнными в БД метаданными, без актуальных ссылок, старше 24 часов; сверка всего bucket после сбоев транзакций остаётся отдельной задачей.
- Перед настоящими клиентами подключить SMS, официальную интеграцию оплаты/чеков, мониторинг, резервные копии и ограничения входящего трафика. Большие видео потребуют фоновой проверки, транскодирования и CDN; текущий лимит — 40 MiB, проверка контейнерного заголовка, без такого медиапайплайна.

Не запускайте Django tests с облачным production `DATABASE_URL`: тестам нужна отдельная PostgreSQL база с правом `CREATEDB`.
