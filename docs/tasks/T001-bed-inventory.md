# T001: бронирование мест и уведомления сотрудников

## Запрос владельца, 12 ноября 2026

Один физический номер содержит несколько отдельно бронируемых мест. Разные клиенты могут жить в нём в пересекающиеся даты; у каждого свои заезд/выезд. Например, номер 102 содержит 102a, 102b, 102c. Один заказчик может забронировать несколько мест в одном номере. План размещения показывает отдельную строку для каждого места, больше прошедших и будущих дней. В кабинете менеджера нужен раздел уведомлений о новых бронях со ссылкой на бронь; он работает и на сайте, и в приложении.

Это спецификация будущего изменения, а не описание уже реализованной системы. Упоминание изменения оплаты не задаёт новой формулы: сохранить текущую оплату за человека/сутки, markup, online/onsite и возвраты до отдельного решения владельца.

## A. Модель и миграция инвентаря

1. Оставить Room физическим номером и владельцем медиа/класса/сезонных цен. Добавить RoomPlace с постоянным ID, номером внутри комнаты, меткой a/b/.../z/aa и состоянием active/maintenance. Количество мест задаётся при создании номера; вместимость согласована с активными местами, без двух независимых счётчиков.
2. Booking остаётся заказом с владельцем, платежами, гостями, документами. Добавить BookingAllocation: booking + place + диапазон проживания. Для нового заказа несколько allocations имеют одинаковые даты и относятся к одному номеру. Разные заказы на соседних местах могут иметь разные даты. Не добавлять раздельные даты внутри одного заказа без отдельной задачи.
3. PostgreSQL exclusion constraint запрещает пересечение активных allocations одного места по [start,end). Удержание до оплаты занимает конкретные места; отмена/истечение освобождает их атомарно. Не использовать now() в условии индекса: явное состояние allocation обновляется сервисом.
4. Блокировка resort/room и согласованный порядок блокировки мест, транзакционное выделение всех мест либо ни одного. Два клиента не могут купить последнее место одновременно. Последовательный выбор нескольких мест в UI не является резервированием.
5. Существующий room-level exclusion сейчас запрещает совместное размещение: снять его только после backfill allocations и установки новых ограничений. Старые активные брони блокируют ВСЕ места номера на прежний срок, чтобы миграция не продала ранее обещанное пространство. Исторические суммы/snapshots/чеки не пересчитывать.
6. Миграция в этапах expand → backfill → validate → переключение чтений/записей → снятие старого ограничения. Проверка на копии PostgreSQL, dry-run отчёт и документированный forward recovery. Не запускать необратимый backfill в production автоматически.
7. Удалять/уменьшать места с историей нельзя: деактивация с сохранением истории; активные/будущие обязательства блокируют вывод места. Смена capacity не должна молча менять проданные места.

## B. Бронь, цена, платежи, документы

1. В клиентском выборе — класс, даты, состав гостей, количество доступных мест/номер. Сервер назначает стабильные place IDs в выбранном физическом номере; заказ не распределяется между разными комнатами молча. Показывать, что размещение совместное и сколько мест бронируется.
2. Каждый проживающий занимает место, включая детей; действующую возрастную ценовую льготу сохранять отдельно от инвентаря. Пример: 2 платных гостя × 20 000 × 7 = 280 000 базовой стоимости; текущая комиссия добавляется по действующим paymentTerms. Количество allocations не должно повторно умножать цену.
3. Один заказ — один frozen total/onlineAmount/onsiteAmount и существующий подтверждённый сервером платёж. Частичные отмены, оплата каждого места отдельно и новый split платежей вне задачи. Подтверждение оплаченного заказа активирует все его места атомарно.
4. Availability, месячный календарь, quote, create, holds, expiration, payment callback, отмена, QR, onsite settlement, check-in/out, автоматический выезд, документы, аналитика должны использовать новый инвентарь. Удалить остаточные room-overlap проверки, мешающие совместному проживанию.
5. QR относится к заказу и показывает все места. Повторный скан не дублирует onsite collection. Документы и roster остаются едиными на booking ID, primary contact берётся из связанного профиля. Доступ после checkout/release сохраняется.
6. Старые и новые native/web клиенты: явно определить совместимость API. Если старый клиент не может безопасно выбирать места, вернуть понятное update_required, а не продать целый номер или проигнорировать guests. Версионировать новые поля, задокументировать переход.

## C. План размещения и календарь

1. Группа «102», строки 102a/102b/102c; сворачиваемая группа. Отдельные полосы разных заказов с собственными датами. Клик открывает конкретную бронь. Один заказ на 2 места отображается в 2 строках без удвоения финансовых итогов.
2. По умолчанию 14 дней назад + сегодня + 45 вперёд. Переключатели 30/60/90 дней, назад/вперёд, «Сегодня», произвольный диапазон. Сервер ограничивает один запрос максимум 120 днями; дальняя история/будущее доступны последовательными окнами.
3. Sticky заголовок дат и колонка мест, горизонтальный scroll, виртуализация строк/колонок при необходимости, компактный мобильный вид без уменьшения touch targets. Не скачивать всю историю всех объектов в workspace.
4. Состояния: фиолетовый — завершённое проживание, синий — заселён, зелёный — оплаченная будущая бронь; pending hold отдельным нейтральным цветом с таймером. Подписи/легенда, не только цвет. Плановый срок и фактические события различаются; пользоваться утверждённым серверным auto-checkout.
5. Клиентский календарь считает доступные МЕСТА в подходящем номере, а не сумму свободных мест разных комнат для одного заказа. Полный выбранный диапазон выделен. Не раскрывать имена соседей/чужие booking IDs.

## D. Уведомления менеджеров

1. Постоянная StaffNotification в общей БД, tenant scope по актуальному владению объектами. Событие + получатель, unique dedup key; unread/read с идемпотентной отметкой, cursor pagination и unread count.
2. При создании pending заказа: «Новая заявка, ожидает оплаты». При verified payment: «Бронь оплачена». Отмена/истечение — соответствующее событие. Создание уведомления в той же транзакции или через transactional outbox, без потерь/дублей при retries.
3. Отдельный раздел «Уведомления» и колокольчик/badge в staff shell сайта и приложения. Ссылка ведёт на конкретный заказ в плане/карточке. Проверять права заново при открытии; отозванный менеджер не видит старые уведомления чужого объекта.
4. Базовая доставка: загрузка при входе/возврате на экран, polling около 30 секунд только в foreground с backoff; отметка прочитанного сохраняется между устройствами. Это работает без платного realtime-сервиса.
5. Background push — отдельный транспорт: FCM для Android и APNs для iOS, device tokens с отзывом и приватными server credentials, локализованные сообщения без персональных данных. Реализовать интерфейс/outbox adapter и настройки; если кабинеты/ключи отсутствуют, записать конкретные необходимые действия владельца. Не выдавать foreground polling за push в закрытом приложении.
6. Исключить accountant из операционных уведомлений, admin имеет платформенный обзор, manager только свои объекты. Полный ИИН, roster, платёжные секреты не помещать в payload, push или logs.

## E. Проверки и завершение

- PostgreSQL: миграция старой полной брони; два клиента на разных местах одной комнаты; конфликт одного места; параллельная покупка последнего; многоместный заказ all-or-nothing; hold expiry и cancellation; раздельные даты соседей; повтор payment/QR; неизменность legacy snapshots.
- Финансы: цена умножается на платных гостей ровно один раз, frozen online/onsite/refunds прежние. Документы видны только owner после checkout/release.
- Notifications: scope/revocation, dedup, pagination/read across sessions, ссылка на нужную бронь, transaction rollback не оставляет ложное уведомление.
- Frontend: demo/API согласованы, RU/KK/EN parity, клиентский календарь и staff planner на 360/390 px и desktop; многоместный заказ читаем, нет horizontal page overflow.
- Выполнить обязательные команды AGENTS.md, backend тесты на PostgreSQL, migration drift check. Native сборки только для проверки затронутых мостов/transport; установка и выдача APK отдельно.
- Обновить architecture, API contract, decisions и verification фактическими изменениями. Старые инструкции о room-level inventory скорректировать после реализации, не до неё.
- Итог в docs/agent-tasks.md: этапы A–E, миграции и совместимость, результаты проверок, commit, оставшиеся настройки push. Не объявлять production готовым без отдельного release.

## Готовность

Три места одной комнаты продаются независимо без overbooking; заказчик занимает несколько мест одним заказом; соседние брони имеют разные даты; planner показывает все места и длинное окно; manager получает постоянные уведомления со ссылками на web/native; финансовая и документная история сохранена. Недоступные push credentials фиксируются отдельным blocker транспорта и не блокируют рабочий in-app inbox.
