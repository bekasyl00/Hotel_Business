## Телефонная регистрация — web, iOS, Android

Реализован серверный адаптер SMSC.KZ по официальному контракту:
https://smsc.kz/api/http/send/ — JSON POST /rest/send/, apikey, phones, mes, sender, fmt=3.
Реальный код никогда не возвращается фронтенду. Код истекает через 5 минут, доступно 5 попыток;
повторная отправка — через 60 секунд, общие PostgreSQL лимиты по телефону/IP и за 24 часа.
После неоднозначной сетевой ошибки POST не повторяется автоматически: cooldown и бюджет сохраняются.
Ответ API означает приём отправки провайдером, не доставку абоненту. Phone verified выставляется только после верного кода.

Закрытые server env (не VITE_*, не Git):

```dotenv
DEBUG=false
GUEST_AUTH_DEMO_OTP=false
GUEST_AUTH_ALLOW_UNVERIFIED_REGISTRATION=false
GUEST_OTP_PROVIDER=smsc
SMSC_API_KEY=
SMSC_SENDER=
GUEST_OTP_DAILY_LIMIT=100
```

Заполнить sender после одобрения SMSC и server key из кабинета. Значение 100 — ограничение попыток, не бюджет в тенге;
дополнительно ограничить расходы/сегменты в кабинете. Без провайдера регистрация/reset закрыты, существующий login остаётся.
По явному решению владельца временный обход действует по server flag без DEBUG; старые демо-challenge не действуют в production.
Старым аккаунтам не присваивается phone_verified автоматически; прохождение настоящего reset подтверждает владение номером.

Порядок: миграции 0021/0022 → секреты сервера → offline preflight → Django check --deploy → API → web/apps.
**Текущая временная поставка:** GUEST_AUTH_ALLOW_UNVERIFIED_REGISTRATION=true, DEBUG=false, demo OTP=false. Регистрация работает без SMS на сайте и native; сброс без подтверждения закрыт. Перед полноценным запуском выключить временный flag и принять реальную SMS-доставку.
Native API `/api/v1/mobile-auth/{configuration,challenges,register,reset}` уже реализован;
scopeToken живёт только в памяти приложения, access/refresh — в существующем защищённом хранилище.
Сначала проверить доставку на своём номере, регистрацию, неверный код, resend, reset/отзыв старой сессии на web/iOS/Android.
Пересборка/установка бинарников и физическая проверка после подключения обязательны; Vite build:apps не является установкой.
WhatsApp Cloud API ещё не реализован; для стартового пилота выбран SMSC, а не личный WhatsApp-бот.

## Проверка конфигурации

```sh
backend/.venv/bin/python scripts/production-preflight.py --env-file /absolute/private/production.env
```

Не вводить значения секретов в командную строку. Скрипт выводит только имена отсутствующих/опасных настроек.
Он не подтверждает доставку SMS, валидность ключа, расположение данных, настройку TLS/S3 или банковский договор.
Флаги проверки провайдера нельзя включать для обхода проверки: сначала сверка реальных результатов.

## Восстановление PostgreSQL

`rehearse-postgres-restore.py` принимает стандартные PG* переменные и только локальный PGHOST.
Пароли — через закрытый pgpass, не аргументы. Работать с изолированной синтетической копией и остановить записи в неё.

```sh
PGHOST=127.0.0.1 PGPORT=54339 PGUSER=tynys_test PGDATABASE=tynys_test \
  backend/.venv/bin/python scripts/rehearse-postgres-restore.py
```

PostgreSQL CLI должны быть в PATH. Скрипт создаёт отдельную случайно названную БД,
сохраняет dump в закрытой временной папке и сравнивает таблицы, число строк и SHA-256 канонического содержимого. Источник не изменяет и БД не удаляет.
Это выполнено локально на синтетических данных. Не доказаны RPO/RTO, PITR/WAL, восстановление прав runtime-роли,
приватных объектов S3 и отдельного DOCUMENT_DATA_ENCRYPTION_KEYS keyring.
Перед боевым запуском повторить полное восстановление в независимой среде, расшифровать тестовый roster,
скачать его документ и сверить платёжный реестр. Ключи резервировать отдельно от дампа.

## Финансовая приёмка

Автотесты `commerce` проверяют полные/частичные возвраты, суммы/идентичность провайдера,
повторы/неоднозначные POST, изоляцию tenant и сред, отдельные online/onsite суммы и неизменность документов.
В текущем проходе внешние платежи/возвраты не выполнялись.

| Сценарий перед запуском | Доказательство от провайдера + платформы |
|---|---|
| Успешная online оплата | Проверенный GET, точная сумма комиссии, confirmed, одна проводка |
| Повтор callback | Та же бронь/проводка, нет второго списания |
| Поздняя оплата после hold | Reconciliation без продажи уже занятого места |
| Полный возврат >=48ч | Независимый verified refund на всю online сумму |
| Частичный возврат 24–48ч | Verified refund 70% online суммы, корректное округление |
| Менее 24ч | Возврат 0 по зафиксированной политике |
| Timeout создания/возврата | Сверка ранее созданного объекта, нет повторного неоднозначного POST |
| Оплата на месте | Только staff attestation; не увеличивает онлайн-поступления платформы |
| Документы | После checkout, разрешения сотрудника, только владельцу, исходные выданные файлы неизменны |

Не делать реальные финансовые операции автоматически ради зелёного отчёта.
Банковская приёмка требует согласованного тестового бронирования, сумм и доступа владельца.

## Короткие номера

Новые и исторические брони получают уникальный отображаемый номер `TYNYS-` + 10 букв/цифр, без I/O/0/1.
UUID API, merchant references, платёжные снимки и подписанный QR не меняются.
Сотрудник может искать билет по короткому номеру; старый `TYNYS-UUID` остаётся допустимым.
Код не является паролем: обязательны вход сотрудника, область санатория и допустимый статус.
Миграция исторических строк требует окна без записи броней; неизвестный код не открывает чужие данные.
